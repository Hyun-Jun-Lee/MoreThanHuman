# Free conversation access and locked entry points

## Goal Capsule

무료 사용자는 대화를 동시에 1개 보유할 수 있고, 삭제하면 새 대화를 만들 수 있어요. 홈·대화 탭은 아직 만들지 않은 추가 대화 자리를 잠금 상태로 설명해요. 서버의 생성 제한과 모바일 잠금 UI를 함께 구현하되 결제 기능이 준비될 때까지 정책 스위치를 꺼 두어요. `free`/`advance`/`plus`의 가격과 상위 플랜별 한도는 아직 정하지 않아요.

정책 활성화 전에 이미 15턴을 넘긴 무료 대화는 남아 있지만 이후 추가 발화는 제한해요. 이 계획은 현재 확정된 제품 규칙을 기준으로 하고, 요금제별 가격과 한도는 결제 단계에서 정해요.

---

## Product Contract

### Problem Frame

현재 홈은 최근 대화 최대 2개를 파스텔 카드로, 대화 탭은 실제 대화 전체를 간결한 행으로 보여줘요. 두 화면 모두 새 대화 진입을 제공하고, 자유 대화와 역할극의 생성 경로가 달라요. 서버의 프로필·대화 모델과 API에는 구매 권한 정보나 대화 생성 한도가 없어요. 대화 삭제는 하드 삭제이며, 삭제 후 빈 자리를 다시 사용할 수 있다는 이번 정책과 맞아요.

기존 `STRATEGY.md`는 무료 Topic Prep 2회와 대화 5 user turns를 기본 체험 한도로 명시했어요. 이번 결정은 Topic Prep 횟수 제한을 없애고, 대화마다 15 user turns로 바꿔요. 단품으로 추가한 대화에도 무료 플랜의 15턴 한도를 적용해요.

### Requirements

- R1. 정책이 활성화되면 무료 계정의 동시 보유 한도는 대화 1개예요. `ACTIVE`와 `COMPLETED`를 포함한 저장된 대화 수를 세고, 삭제하면 새 대화를 만들 수 있어요.
- R2. 기존 무료 계정에 이미 여러 대화가 있으면 기존 대화를 모두 열람하고 이어갈 수 있어야 해요. 정책 활성화 시점의 보유 개수까지는 삭제 후 재생성할 수 있으며, 기존 대화 자체에는 자물쇠를 붙이지 않아요.
- R3. 홈에서는 실제 최근 대화를 파스텔 카드로, 대화 탭에서는 실제 대화를 간결한 행으로 유지해요. 추가 대화가 필요한 상태에는 레코드가 아닌 별도 잠긴 추가 대화 자리를 각 화면의 형식에 맞게 표시해요.
- R4. 홈의 `＋ 새 대화`와 대화 탭의 `＋`는 같은 한도 상태를 반영해요. 한도 초과 시 자유 대화·역할극 준비 흐름을 시작하기 전에 이유와 다음 행동을 알려줘요.
- R5. 생성 한도는 자유 대화의 텍스트·음성 시작과 역할극 시작에 동일하게 적용해요. 직접 API 요청이나 동시 요청으로 우회할 수 없어야 해요.
- R6. 단품 결제 1회는 대화 동시 보유 한도를 영구적으로 1칸 늘려요. 특정 대화에 묶지 않고, 대화를 삭제하면 빈 칸에 새 대화를 만들 수 있어요.
- R7. 무료 Topic Prep 횟수 제한은 두지 않고, 무료 플랜의 각 대화에서 사용자 턴을 15회로 제한해요. 단품 이용권으로 추가한 대화도 이 한도를 따라요.
- R8. 서버 제한과 모바일 잠금 UI는 동일한 정책 스위치가 꺼져 있는 동안 적용하지 않아요. 결제 기능 준비 후 스위치를 켤 때 두 동작이 함께 활성화되어야 해요.
- R9. 구매가 구현되지 않은 상태에서는 가격이나 즉시 결제 동작을 표시하지 않아요. 추후 구매가 연결되면 실제 상품 정보, 복원, 취소·환불 후 권한 상태를 반영해요.
- R10. 정책 활성화 전에 이미 15 user turns를 넘긴 무료 대화는 열람할 수 있지만 추가 발화는 즉시 제한해요.

### Settled Decisions

- D1. 무료 대화 한도는 누적 생성 횟수가 아닌 동시 보유 수예요. 삭제 후 재생성할 수 있어요.
- D2. 잠금은 아직 생성하지 않은 추가 대화 자리에만 표시하고, 기존 여러 대화는 유지해요.
- D3. 서버 제한과 잠금 UI를 모두 구현하되 결제 기능이 준비될 때까지 둘 다 비활성화해요.
- D4. 단품 결제는 동시 보유 슬롯 1개의 영구 이용권이에요.
- D5. 기존 Topic Prep 2회 제한을 없애고 무료 사용자 턴 한도를 15회로 바꿔요.
- D6. 15 user turns는 계정 전체가 아니라 각 대화의 한도이며, 단품 이용권으로 추가한 대화에도 적용해요.
- D7. 기존 무료 계정에 여러 대화가 있으면 정책 활성화 당시 보유 개수까지 삭제 후 재생성할 수 있어요.
- D8. 정책 활성화 전에 이미 15 user turns를 넘긴 무료 대화는 이후 추가 발화를 즉시 제한해요.

## Planning Contract

### Design Direction

새 사용자의 목록에는 실제 대화가 0개이므로 잠긴 ‘기존 대화’가 생길 수 없어요. 잠금 자리는 대화 레코드를 가짜로 만들지 않고, 홈에서는 실제 대화 카드 아래에 별도 파스텔 `추가 대화` 카드로, 대화 탭에서는 실제 목록과 구분된 잠긴 추가 대화 행 1개로 표현해요. 잠긴 항목을 여러 개 반복하면 실제 대화가 여러 개 있는 것처럼 보일 수 있어요. 자물쇠는 제목·상태 텍스트와 함께 표시하고, 탭하면 권한 안내를 열어요. 결제 경로가 없는 동안 정책 스위치는 꺼져 있어 잠금 UI도 노출하지 않아요.

정책이 켜진 이후에도 실제 기존 대화는 잠그지 않아요. `ConversationStatus.ACTIVE/COMPLETED`는 진행 상태이므로 결제 권한에 재사용하지 않아요. 무료 슬롯이 남아 있을 때는 새 대화 진입이 열려 있고, 슬롯을 모두 사용한 상태에는 잠긴 추가 대화 자리를 표시해요.

### Technical Direction

- 권한 판단은 서버를 단일 기준으로 두고, 클라이언트는 정책 활성 여부·생성 가능 여부·남은 슬롯을 표시해요. `free`/`advance`/`plus` 문자열만으로 화면에서 임의 판정하지 않아요.
- 단품 구매와 구독은 사용자 계정에 연결된 권한 이력으로 분리해 설계해요. 계정별로 정책 활성화 당시 보유 개수를 스냅샷해 최소 보유 한도를 `max(1, 기존 보유 개수)`로 정하고, 영구 구매 슬롯 수를 더해요. 이 기존 보유 개수는 삭제해도 줄지 않아요. 구독 슬롯 수는 요금제 정의가 나온 뒤 추가해요. 구독이 끝나 기존 보유 수가 새 한도를 넘더라도 기존 대화는 유지하고 새 생성만 제한하는 방향이에요.
- 정책 스위치는 서버가 소유하고 클라이언트가 읽을 수 있어야 해요. 기본값은 `off`이고, `off`에서는 기존 생성 API 동작과 기존 두 탭의 UI를 유지해요. 서버와 모바일의 활성화 시점이 엇갈리지 않도록 구매 복원·권한 데이터 준비와 함께 출시 절차를 정의해요.
- 기존 보유 개수 스냅샷은 스위치를 켜는 시점과 일관되어야 해요. 준비 중인 백필과 활성화 사이에 생성·삭제가 끼어도 사용자의 기존 대화 교체 권한을 잘못 줄이지 않도록 전환 절차와 데이터 검증을 마련해요.
- 양쪽 시작 API는 STT·LLM 호출 및 `ConversationModel` 저장 전에 동일한 한도 검사를 수행해요. 동시 요청에는 원자적 예약/카운터 또는 DB 잠금이 필요해요. 현재 `save()`는 즉시 커밋하므로 AI 생성 실패 시 생긴 빈 대화의 처리도 정의해요. 대화 턴 한도는 텍스트·음성·재시도 경로에서 저장 전 일관되게 확인해요.
- 15턴은 대화별 사용자 발화 수로 계산해요. 자유 대화의 첫 사용자 발화는 1턴이고 역할극의 AI 첫 인사는 0턴이에요. 메시지 총수 `message_count`로 환산하지 말고 사용자 발화 자체를 기준으로 세어야 해요. 정책 활성화 전 생성된 대화에도 같은 기준을 적용해요.
- 한도 초과는 안정적인 기계 판독 오류 코드로 반환해요. 클라이언트는 이를 일반 네트워크 오류와 구별해 안내를 표시하고, 홈·대화 탭 권한 상태를 갱신해요.
- 기존 대화의 조회·메시지·turn은 계속 허용해요. 추가 대화 자리에는 대화 ID가 없고, 실제 대화 목록 응답에 섞지 않아요.
- 실제 유료 결제 단계에서는 Apple/Google의 앱 내 디지털 상품 정책을 검토하고, 스토어 구매 검증·복원·구독 변경·환불/취소 이벤트를 서버 권한에 반영해요. 현재 단계에서는 플랜별 가격·상품 ID를 고정하지 않아요.

### Sequencing

권한 계약과 기존 데이터 경과 정책을 문서로 정해요. 서버에서 기본 `off`인 스위치·권한 조회·기존 보유 개수 스냅샷·원자적 생성 차단·대화별 15턴 제한을 구현하고, Flutter 두 탭과 시작·턴 흐름에 같은 상태를 연결해요. 스위치가 꺼진 상태의 회귀 테스트를 통과시킨 뒤 별도 후속 작업으로 스토어 상품, 구매·복원, 환불·만료 처리를 연결해요. 실제 구매 경로와 권한 이행이 준비된 배포에서만 스위치를 켜요.

## Implementation Units

### U1. Product rules and contracts

- **Goal:** 확정된 D1–D8을 `STRATEGY.md`, `docs/mobile-flow-spec.md`, `docs/DSL.md`, `.agent/_contracts/`의 해당 계약에 일관되게 반영해요.
- **Files:** 위 문서, 필요하면 `CONCEPTS.md`.
- **Verification:** 정책 `off/on`, 0/1/여러 대화, 삭제·생성 실패·구독 만료의 동작이 모순 없이 정의되었는지 확인해요.

### U2. Server entitlements and enforcement

- **Goal:** 기본 `off` 스위치, 보유 슬롯 권한 저장·조회, 기존 계정 보유 개수 스냅샷, 두 생성 API의 원자적 차단, 대화별 15턴 차단을 구현해요.
- **Files:** `backend/domains/conversation/`, 권한 도메인 또는 `backend/domains/auth/`, Alembic migration, `docs/DSL.md`.
- **Verification:** 정책 `off/on`, 무료 0/1/여러 개, 기존 계정의 삭제·재생성, 병렬 시작, AI 실패, 각 대화의 14/15/16턴 경계, 단품 슬롯 대화, 다른 계정, 영구 슬롯 구매와 구독 만료를 API 테스트로 확인해요.

### U3. Mobile state and surfaces

- **Goal:** 서버의 스위치·생성 가능·턴 상태를 홈 파스텔 카드와 대화 탭 행에 표현하고, 두 `＋` 진입과 대화 화면의 턴 안내를 같은 정책으로 연결해요.
- **Files:** `mobile/lib/features/home/`, `mobile/lib/features/history/`, `mobile/lib/features/conversation/`, `mobile/lib/app/router/`, `mobile/lib/core/copy/`.
- **Verification:** 정책 `off/on`, 빈 계정·무료 1개·기존 여러 개·구독 계정·오프라인·권한 변경 상태에서 잠금 문구, 탭 행동, 접근성 레이블을 Flutter 테스트로 확인해요.

### U4. Purchase and restoration, when product definitions are ready

- **Goal:** 확정된 단품 상품과 구독을 스토어 구매, 서버 검증, 복원, 갱신·만료·환불과 연결해요.
- **Files:** 후속 구매 도메인, Flutter 결제 연동, 스토어 상품 설정 및 운영 문서.
- **Verification:** iOS·Android 스토어 샌드박스에서 구매·복원·중복 알림·취소 후 권한 반영을 확인해요.

## Verification Contract

구현 후 `backend/`에서 `uv run pytest -q`, `mobile/`에서 `flutter analyze`와 `flutter test`를 실행해요. 병렬 생성과 권한 변경은 단위 테스트만으로 충분하지 않으므로 실제 DB 트랜잭션을 거치는 통합 테스트가 필요해요. 출시 전에는 iOS·Android에서 구매 및 복원 경로를 각각 확인해요.

---

## Definition of Done

정책 `off`에서는 기존 API와 UI 동작이 유지되어야 해요. 정책 `on`에서는 두 탭의 추가 대화 자리가 서버 생성 가능 상태와 일치하고, 기존 대화는 모두 이용 가능해야 해요. 삭제·동시 요청·생성 실패·구독 변경에도 슬롯이나 턴 한도를 우회하거나 정당한 접근을 잃지 않아야 해요. 가격·결제 버튼은 실제 구매 경로가 준비된 뒤에만 노출해야 해요. `STRATEGY.md`, `docs/DSL.md`, 모바일 UX 문서, 관련 changelog를 최종 정책과 동기화해야 해요.
